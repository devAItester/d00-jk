# HTML/CSS optimization: reference vs generated output

## Цель

Проверить, насколько наш генератор действительно воспроизводит модель XXIIVV Wiki, и отделить визуальное сходство от качества и сложности исходного HTML/CSS.

Это не исправление production и не попытка сделать код «современнее» ради самого обновления. Цель — найти объективно лишнюю сложность и сохранить те решения референса, которые непосредственно определяют его поведение и визуальную модель.

## Контрольный материал

Для сравнения зафиксирована одна реальная страница референса:

- upstream: `XXIIVV/oscean`
- страница: `site/home.html`
- CSS: `links/main.css`
- контрольный commit: `7ae8d4a3329fab51389d70fad330717540fb0f57`

Копия исходников сохранена в `development/html-css-optimization/reference/`.

## Что сравниваем

1. **HTML output** — какая разметка фактически попадает в браузер.
2. **CSS** — геометрия, единицы измерения, наследование, reset и layout-модель.
3. **Генератор** — насколько сложна логика, которая создаёт этот output.
4. **Семантика и стандарты HTML** — есть ли объективные проблемы независимо от визуального результата.
5. **Accessibility** — элементы, атрибуты и структура документа.
6. **Производительность и стабильность layout** — только там, где это следует из структуры.
7. **Fidelity** — что необходимо оставить для воспроизведения поведения референса.

## Результаты исследования

### 1. CSS не является главным расхождением

Наш `_includes/style.css` практически буквально совпадает с upstream `links/main.css`.

У reference дополнительно есть:

```css
html {
  background-image:url(../media/icon/halftone.gif);
  background-repeat:repeat;
  background-attachment:fixed
}
```

Это отдельное визуальное свойство, а не другая layout-модель.

**Вывод:** переделывать базовый CSS только ради сходства с reference не требуется.

### 2. В reference units есть

Основная геометрия построена преимущественно на `px`:

`30px`, `45px`, `50px`, `60px`, `624px`, `400px`, `25px`, `15px`, `10px`.

Есть также проценты и `calc()`.

**Вывод:** замена `px` на `rem` не является оптимизацией сама по себе. Для fidelity это скорее потенциальная регрессия.

### 3. Основная дополнительная сложность находится в генераторе меню

Наш `_includes/nav.html` вычисляет текущий узел, parent и grandparent, затем сначала делает проход для определения наличия колонок и ещё три прохода для вывода самих колонок.

Фактически получается:

```text
content tree
  ↓
Liquid: вычисление контекста
  ↓
Liquid: поиск колонок
  ↓
Liquid: вывод column 1
  ↓
Liquid: вывод column 2
  ↓
Liquid: вывод column 3
  ↓
обычный HTML <nav><ul>...</ul>...</nav>
```

Это не обязательно ошибка: алгоритм действительно реализует локальный срез дерева. Но это первый явный кандидат на оптимизацию **генератора**, потому что браузеру вся эта сложность не нужна.

### 4. Inline CSS — реальное архитектурное отличие, но пока не доказанная проблема

Reference подключает:

```html
<link href="../links/main.css" rel="stylesheet">
```

Наш layout встраивает CSS непосредственно в документ:

```html
<style>{% include style.css %}</style>
```

Это даёт два противоположных эффекта:

- плюс: для первого документа нет отдельного CSS-запроса;
- минус: один и тот же CSS повторяется в каждом HTML-документе и не может быть использован browser cache как отдельный ресурс.

Это **trade-off**, а не автоматическая ошибка.

Поскольку ранее inline CSS был выбран сознательно, менять его на этом этапе не будем. Сначала нужно измерить реальный размер output и количество страниц.

### 5. HTML reference содержит исторические решения, которые не следует копировать автоматически

В контрольной странице обнаружены:

- page-specific `<style>`;
- inline `style`;
- пустой `<ul></ul>`;
- явные размеры отдельных изображений;
- старые/исторические элементы и приёмы.

Следовательно:

> reference является эталоном поведения и визуальной модели, но не безусловным эталоном качества HTML.

Мы должны воспроизводить намерение, а не механически копировать каждую историческую деталь.

### 6. Наш logo.svg имеет собственные intrinsic dimensions

В нашем `assets/logo.svg` явно указано:

```xml
<svg ... width="200" height="42" viewBox="0 0 200 42" ...>
```

При этом HTML содержит:

```html
<img src="{{ '/assets/logo.svg' | relative_url }}" alt="{{ site.title }}">
```

То есть размеры отсутствуют на самом `img`, но присутствуют в SVG-ресурсе.

WHATWG HTML Standard допускает и рекомендует задавать размеры изображения через `width`/`height`; эти размеры позволяют user agent заранее зарезервировать место и определить aspect ratio. Спецификация отдельно отмечает значение этого подхода для предотвращения layout shift. citeturn1search0turn1search10turn1search12

Однако в нашем конкретном случае нельзя пока объявлять это причиной наблюдаемой встряски: SVG уже содержит intrinsic `200×42`.

**Статус:** проверить экспериментом, а не исправлять предположением.

### 7. HTML document language

Наш layout начинается с:

```html
<!DOCTYPE html><html id="lo">
```

То есть `lang` отсутствует.

WHATWG определяет `lang` как атрибут, задающий основной язык содержимого элемента. citeturn1search13

Это уже не вопрос визуальной fidelity, а качества документа/accessibility.

Но здесь тоже сначала нужно определить язык сайта и правила для смешанного контента. Простое добавление `lang="en"` без проверки всего контента было бы преждевременным.

**Статус:** кандидат на исправление после baseline.

### 8. Validation ≠ полная оценка качества

Для следующего этапа используем HTML validation, но не будем считать результат validator единственным критерием.

W3C прямо разделяет validity и conformance: validator проверяет синтаксическую корректность, но validity не является полной проверкой качества документа. citeturn1search11turn1search15

Поэтому проверка будет состоять из:

- conformance/validation;
- semantics;
- accessibility;
- layout stability;
- output size;
- generator complexity;
- fidelity.

## Важное ограничение текущего этапа

GitHub connector позволяет проверить исходные файлы и commit, но не даёт нам сейчас локальный generated artifact GitHub Pages для произвольного commit.

Поэтому **буквальный diff generated HTML vs reference HTML ещё не объявляется завершённым**.

На этом этапе мы сравнили source/template architecture и зафиксировали кандидатов. Следующий шаг — получить реальный generated HTML из локального Jekyll build или deploy artifact и только после этого делать количественные выводы о размере и структуре output.

Это важно: не подменять фактическое измерение предположением о том, что Liquid «наверняка» генерирует.

## Метод работы

После каждого существенного изменения фиксируем:

- что изменено;
- какую проблему оно решает;
- почему исходный вариант был хуже;
- влияет ли изменение на output;
- влияет ли оно на визуальное поведение;
- влияет ли оно на accessibility/валидность;
- есть ли цена или новый компромисс.

Production на этапе исследования не меняется.

## Рабочий принцип

Визуально отличный прототип не является основанием прекращать оптимизацию.

HTML и CSS — часть архитектуры. Они определяют не только внешний вид, но и размер output, layout-модель, устойчивость документа, accessibility, кэширование ресурсов и количество логики, которую приходится поддерживать генератору.

Поэтому задача — не «переделать рабочий сайт», а найти минимальную и устойчивую реализацию того же результата.
